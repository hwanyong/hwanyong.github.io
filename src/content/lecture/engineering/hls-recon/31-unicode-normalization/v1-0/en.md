## 31.1 문제 — 눈에 같은 두 폴더

`hls-recon` 을 두 번 실행했더니 같은 자리에 폴더가 둘 생겼다고 하자.

```
그렌라간/
그렌라간/
```

터미널에서도, Finder 에서도, 이 문서에서도 두 이름은 **글자 하나 다르지 않게 보인다.**
그러나 파일 시스템은 둘을 다른 이름으로 취급했고, 27화 중 앞의 몇 화는 이쪽에,
나머지는 저쪽에 들어갔다.

바이트를 보면 즉시 갈린다.

```
$ python3 -c "
import unicodedata as u
for f in ('NFC','NFD'):
    s = u.normalize(f, '그렌라간')
    print(f, len(s), s.encode('utf-8').hex())
"
NFC 4 eab7b8eba08ceb9dbceab084
NFD 10 e18480e185b3e18485e185a6e186abe18485e185a1e18480e185a1e186ab
```

**같은 네 글자가 4개 코드포인트 12바이트이기도 하고, 10개 코드포인트 30바이트이기도
하다.** `그` 하나가 `ᄀ`(초성 기역 U+1100) + `ᅳ`(중성 으 U+1173) 둘로 쪼개지고,
`렌` 은 초성·중성·종성 셋으로 쪼개진다. 렌더링 엔진이 그것을 다시 한 음절로 합쳐
그리기 때문에 눈에는 같다.

> **용어** — **코드포인트(code point)**: 유니코드가 문자 하나에 부여한 번호.
> `U+AC00` 처럼 쓴다. **바이트 수**(UTF-8 인코딩 결과)와도, **화면에 보이는 글자
> 수**(자소 클러스터)와도 다르다. 이 장은 그 셋이 어긋나는 이야기다.

`==` 로 견주면 당연히 다르다. `len()` 도 다르다. 정렬 순서도 다르다. 해시도 다르다.
**문자열을 다루는 모든 연산이 다른 답을 낸다.** 그런데 사람의 눈은 같다고 말한다.

이 저장소에서 이 상황이 실제로 만들어지는 경로는 다음 둘이 만나는 지점이다.

| 출처 | 표기 형태 | 근거 |
|---|---|---|
| 웹에서 받은 작품명 | 대개 **NFC** | HTML·JSON 은 대부분 NFC 로 작성·전송된다 |
| 파일 시스템에서 읽은 이름 | **볼륨이 정한다** | HFS+ 는 분해형, exFAT·ext4 는 쓴 그대로, APFS 는 쓴 그대로 |

`inventory.stock_for` 는 이 둘을 견주는 함수다([`inventory.py:214-256`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L214-L256)). 견주기 전에
표기를 맞추지 않으면, **이미 받아둔 27화를 못 알아보고 전부 다시 받는다.**

## 31.2 원리 — 정준 동치와 호환 동치

### 31.2.1 유니코드는 "같은 문자"를 두 층으로 정의한다

유니코드는 같은 글자를 표현하는 방식이 여럿 존재하는 것을 허용한다. 라틴 문자
`Å` 는 `U+00C5`(합성된 하나)일 수도 있고 `A`(U+0041) + `◌̊`(U+030A COMBINING RING
ABOVE) 둘일 수도 있다. 한글 `그` 는 `U+ADF8` 하나일 수도 있고 초성·중성 둘일 수도
있다. 이 중복은 역사적 사고가 아니라 **기존 문자 집합과의 왕복 변환을 보장하려는
설계 결정**이다.

중복을 허용했으므로 "같음"의 정의가 필요해진다. 유니코드는 두 층으로 정의한다.

> **용어** — **정준 동치(canonical equivalence)**: 두 문자열이 **같은 문자**를
> 나타내며, 어떤 문맥에서도 서로 바꿔 써도 의미가 바뀌지 않는 관계.
> `Å`(U+00C5) 와 `A`+`◌̊` 가 그렇다.

> **용어** — **호환 동치(compatibility equivalence)**: 두 문자열이 **다른 문자**이지만
> 같은 추상 문자에서 파생된 관계. 서식·폭·위치가 다르다. `ﬁ`(U+FB01 합자) 와 `fi`,
> `①` 과 `1`, 전각 `Ａ` 와 `A` 가 그렇다. **바꿔 쓰면 정보가 사라진다.**

정준 동치는 "표기만 다르고 같은 글자", 호환 동치는 "다른 글자인데 뜻이 통함"이다.
이 구분이 뒤 절 전체를 지배한다.

### 31.2.2 두 축이 네 형식을 만든다

정규화 형식은 **어떤 동치를 쓰는가**(정준 / 호환)와 **결과를 합칠 것인가
쪼갤 것인가**(합성 / 분해)의 조합이다.

> **용어** — **정규화(normalization)**: 동치인 여러 표현 중 하나를 대표로 정해
> 문자열을 그 대표형으로 바꾸는 연산. 규정은 UAX #15(Unicode Normalization Forms).

| 형식 | 정식 이름 | 동치 | 방향 | 한 줄 정의 |
|---|---|---|---|---|
| **NFD** | Normalization Form Canonical Decomposition | 정준 | 분해 | 정준 분해까지만 하고 멈춘다 |
| **NFC** | Normalization Form Canonical Composition | 정준 | 합성 | 정준 분해한 뒤 **다시 정준 합성**한다 |
| **NFKD** | …Compatibility Decomposition | 호환 | 분해 | 호환 분해까지 한다 |
| **NFKC** | …Compatibility Composition | 호환 | 합성 | 호환 분해한 뒤 **정준** 합성한다 |

`K` 는 compatibility 의 K 다(C 가 이미 Composition 에 쓰여서). 그리고 이름과 달리
**NFC 도 내부적으로 한 번 분해한다.** 분해 없이 합성만 하면 결합 문자의 순서가
표준 순서로 정렬되지 않아 같은 글자가 여전히 두 표현으로 남기 때문이다.

> **용어** — **정준 순서(canonical ordering)**: 결합 문자(combining mark)가 여럿
> 붙을 때 **정준 결합 클래스(canonical combining class)** 값 순으로 정렬하는 규칙.
> 분해 단계에서 이 정렬이 이루어진다.

실측한 네 형식의 결과다.

| 입력 | NFC | NFD | NFKC | NFKD |
|---|---|---|---|---|
| `가` U+AC00 | `가` (1자) | `가` (2자) | `가` (1자) | `가` (2자) |
| `ﬁ` U+FB01 합자 | `ﬁ` | `ﬁ` | **`fi`** | **`fi`** |
| `①` U+2460 | `①` | `①` | **`1`** | **`1`** |
| `Ａ` U+FF21 전각 | `Ａ` | `Ａ` | **`A`** | **`A`** |
| `／` U+FF0F 전각 슬래시 | `／` | `／` | **`/`** | **`/`** |
| `ㄱ` U+3131 호환 자모 | `ㄱ` | `ㄱ` | **`ᄀ`** U+1100 | **`ᄀ`** U+1100 |
| `½` U+00BD | `½` | `½` | **`1⁄2`** | **`1⁄2`** |

**정준 형식(NFC/NFD)은 호환 문자를 건드리지 않는다.** `ﬁ` 합자는 NFC 를 통과해도
그대로 `ﬁ` 다. 반대로 NFKC 는 `／`(전각 솔리더스)를 **ASCII `/` 로 바꿔 놓는다** —
이 사실이 §31.7.3 의 핵심이 된다.

### 31.2.3 NFC 도 코드포인트를 바꾼다 — 정준 특이 분해

"NFC 는 합성만 하니까 코드포인트가 늘지도 줄지도 않는다"는 직관은 틀렸다.

> **용어** — **정준 특이 분해(canonical singleton decomposition)**: 한 코드포인트가
> 결합 문자 없이 **다른 코드포인트 하나**로 정준 분해되는 경우. 같은 글자를 두 번
> 부호화해 버린 역사적 중복을 정리하는 장치다.

실측한 셋이다.

| 입력 | 이름 | NFC 결과 | 비고 |
|---|---|---|---|
| `K` U+212A | KELVIN SIGN | **`K` U+004B** | ASCII 대문자 K 가 된다 |
| `Å` U+212B | ANGSTROM SIGN | `Å` U+00C5 | NFD 로는 `A`+`◌̊` 둘 |
| `Ω` U+2126 | OHM SIGN | `Ω` U+03A9 | 그리스 대문자 오메가 |

**NFC 하나만으로 비ASCII 문자가 ASCII 문자로 바뀐다.** "우리는 NFKC 같은 위험한 건
안 쓰고 NFC 만 쓰니까 괜찮다"는 방어 논리가 성립하지 않는 지점이며, §31.7.2 에서
다시 든다.

## 31.3 파일 시스템은 어느 형식으로 돌려주는가

이 코드의 주석은 macOS 를 두 번 지목한다([`naming.py:123`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/naming.py#L123), [`inventory.py:208`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L208)).
실제로 무슨 일이 일어나는지는 **볼륨의 파일 시스템에 달렸고**, 그 동작은 두 축으로
갈린다.

> **용어** — **정규화 보존(normalization-preserving)**: 만들 때 준 표기를 그대로
> 저장하고 그대로 돌려준다.
> **정규화 불변(normalization-insensitive)**: 정규화 형식이 달라도 **같은 이름으로
> 찾아준다.** 둘은 독립된 성질이다.

| 파일 시스템 | 저장 시 | 조회 시 | 같은 글자의 두 표기가 공존하는가 |
|---|---|---|---|
| **HFS+** | 분해형(NFD 변종)으로 **바꿔서** 저장 | 형식 무관하게 찾음 | 불가 |
| **APFS** (macOS 10.13+) | **준 그대로** 저장 | 형식 무관하게 찾음 | 불가 |
| **exFAT** | 준 그대로 | 바이트 그대로 견줌 | **가능** |
| **ext4** (Linux 기본) | 준 그대로 | 바이트 그대로 견줌 | **가능** |
| **SMB·NFS 공유** | 서버 구현에 달림 | 서버 구현에 달림 | **가능** |

이 문서를 쓰며 이 저장소의 작업 볼륨(APFS, Darwin 25.5.0)에서 직접 측정한 결과다.

```
$ python3 -c "
import unicodedata as u, pathlib
d = pathlib.Path('t'); d.mkdir()
(d / (u.normalize('NFC','그렌라간') + '.txt')).write_text('x')
n = next(d.iterdir()).name
print('읽어온 이름이 NFC 인가:', u.normalize('NFC', n) == n)
print('읽어온 이름이 NFD 인가:', u.normalize('NFD', n) == n)
print('NFD 경로로도 열리는가 :', (d / (u.normalize('NFD','그렌라간') + '.txt')).exists())
"
읽어온 이름이 NFC 인가: True
읽어온 이름이 NFD 인가: False
NFD 경로로도 열리는가 : True
```

**NFC 로 만들었더니 NFC 로 돌아왔고, NFD 경로로도 같은 파일이 열렸다.** 반대로 NFD
이름으로 만들면 NFD 로 돌아온다(같은 방법으로 확인). 즉 오늘의 APFS 는 **보존하면서
불변**이다.

여기서 코드의 서술과 실측이 어긋난다. `sanitize` 의 독스트링은 이렇게 적혀 있다.

> **용어** — **독스트링(docstring)**: 함수·클래스·모듈의 첫 문장 자리에 놓인 문자열
> 리터럴. `#` 주석과 달리 실행 시각에 `__doc__` 로 남아 `help()` 와 문서 생성기가
> 읽는다. 즉 **코드의 일부로 배포되는 설명**이다.

```python
# naming.py:123-124
    macOS 파일 시스템은 한글을 자모 분리형(NFD)으로 저장하지만, 웹에서 받은 이름은
    완성형(NFC)이다. 섞이면 눈에 같아 보이는 두 폴더가 생기므로 NFC 로 고정한다.
```

이 서술은 **HFS+ 에서는 정확하고 APFS 에서는 정확하지 않다.** 그렇다고 이 코드가
불필요해지는 것은 아니다. NFD 이름이 이 도구에 도달하는 경로가 여전히 여럿이다.

| 경로 | 왜 NFD 인가 |
|---|---|
| HFS+ 볼륨(오래된 외장 디스크·타임머신 백업) | 파일 시스템이 저장 시 분해한다 |
| macOS 에서 만든 ZIP·TAR 를 푼 결과 | 아카이브에 분해형 이름이 그대로 들어간다 |
| macOS ↔ Linux 사이의 `rsync`·SMB 공유 | 전달 계층이 표기를 바꾸지 않고 옮긴다 |
| 브라우저가 내려받은 파일의 저장 이름 | 저장 대화상자·다운로드 관리자 구현에 달렸다 |

그리고 **NFD 이름이 exFAT·ext4 볼륨에 놓이는 순간** 두 표기가 공존할 수 있게 된다.
[`naming.py:25`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/naming.py#L25) 가 "외장 디스크가 exFAT 이면 걸린다"고 적어 둔 그 볼륨이다.

## 31.4 코드 — NFC 로 고정하는 두 지점

이 저장소는 정규화를 **딱 두 곳**에서 한다. 두 곳 다 경계이고, 하는 일은 다르다.

![이 코드가 NFC 로 고정하는 두 지점과 각각의 목적](/images/lecture/hls-recon/31-two-pins.svg)

*그림 31-1 — 이 코드가 NFC 로 고정하는 두 지점과 각각의 목적*

### 31.4.1 저장 시 — `sanitize()`

```python
# naming.py:120-130
def sanitize(name: str) -> str:
    """폴더·파일 이름으로 쓸 수 있게 다듬는다.

    macOS 파일 시스템은 한글을 자모 분리형(NFD)으로 저장하지만, 웹에서 받은 이름은
    완성형(NFC)이다. 섞이면 눈에 같아 보이는 두 폴더가 생기므로 NFC 로 고정한다.
    끝의 점·공백은 제거한다 — Windows 에서 열 수 없는 이름이 되고, 외장 디스크나
    네트워크 공유로 옮길 때 그대로 문제가 된다.
    """
    s = _UNSAFE_RE.sub("_", unicodedata.normalize("NFC", name)).strip()
    s = s.rstrip(". ")
    return s or "untitled"
```

이 함수가 **디스크에 남을 이름을 정하는 유일한 지점**이다. 호출 지점은 모두
"쓰기 직전"이다.

| 호출 지점 | 무엇을 정하는가 |
|---|---|
| [`library.py:23`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/library.py#L23) `series_folder` · [`library.py:77`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/library.py#L77) `plan_tidy` | 시리즈 **폴더 이름** |
| [`library.py:33`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/library.py#L33) `place` · [`cli.py:891`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/cli.py#L891) | 저장할 **파일 이름** |
| `series.py:194,314,316` | 사이트에서 읽은 작품명·회차명을 이름으로 확정 |

여기서 순서가 중요하다. **NFC 를 먼저 하고 그다음 예약 문자를 치환한다.** 반대로
하면 어떻게 되는지는 §31.7.3 에서 실측으로 다룬다.

`sanitize` 가 **하지 않는 것**도 설계다. `casefold` 하지 않고, 공백을 없애지 않고,
호환 문자를 펴지 않는다. 이 이름은 사람이 읽고 다른 도구가 열 이름이므로
**원본을 알아볼 수 있어야 하기 때문**이다. 정규화는 딱 정준 동치까지만 — 즉
"같은 글자의 다른 표기"만 통일하고 "다른 글자"는 건드리지 않는다.

### 31.4.2 비교 시 — `_key()`

```python
# inventory.py:205-211
def _key(s: str) -> str:
    """견주기용 표기 — NFC 로 맞추고 공백·구분자를 없앤다.

    macOS 파일 시스템은 한글을 자모 분리형(NFD)으로 돌려주고 사이트가 알려준
    작품명은 완성형(NFC)이다. 정규화하지 않으면 눈에 같은 두 문자열이 어긋난다.
    """
    return re.sub(r"[\s._-]+", "", unicodedata.normalize("NFC", s)).casefold()
```

한 줄에 세 연산이 순서대로 들어 있다.

| 순서 | 연산 | 무엇을 흡수하는가 |
|---|---|---|
| 1 | `normalize("NFC", s)` | 같은 글자의 표기 차이 (NFC ↔ NFD) |
| 2 | `re.sub(r"[\s._-]+", "", …)` | 구분자 차이 (`Sky.Blue` ↔ `Sky Blue` ↔ `Sky_Blue`) |
| 3 | `.casefold()` | 대소문자 차이 (`SKY` ↔ `sky`) |

이 키는 **오직 견주기 위해서만 만들어지고 즉시 버려진다.** `stock_for` 안에서만
쓰인다.

```python
# inventory.py:238-239
want = _key(title)
keys = {stem: _key(stem) for stem in groups}
```

되돌릴 필요가 없으므로 `sanitize` 보다 훨씬 공격적으로 뭉갤 수 있다. **어떤 정보를
버려도 되는지는 그 문자열이 이후에 무엇이 되는지가 정한다** — 이것이 두 함수를
가르는 원리다.

### 31.4.3 `casefold` 와 `lower` 는 다르다

> **용어** — **대소문자 접기(case folding)**: 대소문자 구별을 없앤 **비교 전용**
> 표기를 만드는 연산. `str.lower()`(소문자화)와 목적이 다르다. 소문자화는 "읽을 수
> 있는 소문자 텍스트"를 만들고, 접기는 "같으면 같게 나오는 키"를 만든다.

실측한 차이다.

| 문자 | 코드포인트 | 이름 | `.lower()` | `.casefold()` |
|---|---|---|---|---|
| `ß` | U+00DF | LATIN SMALL LETTER SHARP S | `ß` | **`ss`** |
| `ẞ` | U+1E9E | LATIN CAPITAL LETTER SHARP S | `ß` | **`ss`** |
| `ς` | U+03C2 | GREEK SMALL LETTER FINAL SIGMA | `ς` | **`σ`** |
| `ſ` | U+017F | LATIN SMALL LETTER LONG S | `ſ` | **`s`** |
| `ﬁ` | U+FB01 | LATIN SMALL LIGATURE FI | `ﬁ` | **`fi`** |

**`lower()` 로는 `"STRASSE".lower() != "Straße".lower()` 이지만 `casefold()` 로는
같아진다.** 그리고 접기는 길이를 바꾼다 — `ß` 한 글자가 `ss` 두 글자가 된다.
그래서 접기 결과는 표시용으로 쓸 수 없고, 이 코드도 쓰지 않는다.

한글만 다루는 이 저장소에서 이 선택은 관측 가능한 차이를 만들지 않는다.
한글 음절(U+AC00–U+D7A3) · 조합용 자모(U+1100–U+11FF) · 호환 자모(U+3130–U+318F)
전 범위에서 `casefold` 는 항등 함수임을 확인했다. **그럼에도 `casefold` 가 옳은
이유는 이 함수의 이름이 `_key` 이기 때문이다** — 비교 키를 만드는 자리에 소문자화를
쓰면, 나중에 라틴 문자 제목이 들어왔을 때 조용히 틀린다.

### 31.4.4 구분자까지 없애는 이유

`_key` 는 `[\s._-]+` 를 통째로 지운다. 정규화와 무관해 보이지만 같은 문제의 연장이다.

파일 이름의 줄기는 플레이어 설정의 `title` 에서 오고, 작품명은 목록 페이지에서
온다([`inventory.py:217-219`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L217-L219)). 두 출처는 구분자 관습이 다르다.

| 출처 | 흔한 표기 |
|---|---|
| 파일 이름 (다운로드 도구·릴리스 그룹) | `Sky.Blue`, `Sky_Blue`, `Sky-Blue` |
| 목록 페이지 (사람이 쓴 제목) | `Sky Blue` |

세 단계 매칭(완전 일치 → 작품명이 줄기를 품음 → 줄기가 작품명을 품음,
[`inventory.py:241-251`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L241-L251))은 **부분 문자열 포함**으로 판정한다. 구분자가 남아 있으면
`천원돌파 그렌라간` 안에서 `그렌라간` 은 찾아도 `그렌.라간` 은 못 찾는다.
정규화가 "같은 글자의 표기 차이"를 흡수하듯, 구분자 제거는 "같은 제목의 표기 차이"를
흡수한다. **같은 종류의 결정이 층만 다르게 반복된 것이다.**

## 31.5 이렇게 하지 않으면 무엇이 깨지는가

### 31.5.1 정규화를 빼면 — 27화를 다시 받는다

`_key` 에서 `unicodedata.normalize("NFC", s)` 한 조각만 빼면 어떻게 되는지 재고 조사
경로를 그대로 따라가 보자. 무리가 하나뿐이면 `stock_for` 이 그것을 그대로 돌려주므로
([`inventory.py:234-236`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L234-L236)) `_key` 까지 오지 않는다. 그래서 `--flat` 으로 여러 작품이 한
폴더에 섞인 경우를 놓는다 — 한 무리는 NFD 이름으로 저장된 회차이고, 사이트는 NFC 로
작품명을 알려준다.

| 단계 | 정규화 있음 | 정규화 없음 |
|---|---|---|
| `_key("그렌라간")` (NFD, 디스크) | `그렌라간` (NFC 4자) | `그렌라간` (NFD 10자) |
| `_key("천원돌파 그렌라간")` (NFC, 사이트) | `천원돌파그렌라간` | `천원돌파그렌라간` (NFC) |
| 포함 판정 `k in want` | **참** | **거짓** — 바이트가 다르다 |
| `stock_for` 반환 | 재고 27개 | **빈 재고** |
| 결과 | 빠진 회차만 받는다 | **27화를 전부 다시 받는다** |

`stock_for` 의 독스트링이 이 실패를 미리 적어 두었다 — "가릴 수 없으면 빈 재고를
준다"([`inventory.py:229-230`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L229-L230)). 안전한 실패이긴 하지만, 여기서는 **가릴 수 있는데도
표기 때문에 못 가린 것**이므로 이득이 통째로 사라진다. 재고 조사 모듈의 존재 이유
자체가 "회차마다 페이지·플레이어·XHR 세 번, 27화면 80여 건"의 요청을 아끼는
것이었다([`inventory.py:8-10`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L8-L10)).

실제로 `_key` 가 두 형식을 같게 만드는지 확인했다.

```
$ python3 -c "
import unicodedata as u, sys; sys.path.insert(0,'.')
from hlsrecon.inventory import _key
print(_key(u.normalize('NFC','그렌라간')) == _key(u.normalize('NFD','그렌라간')))
"
True
```

### 31.5.2 이 코드가 아직 못 막는 것 — 그룹 키는 정규화되지 않는다

`_key` 는 **견줄 때** 정규화한다. 그런데 회차를 무리로 묶는 것은 그보다 먼저 일어나고,
그 자리에서는 정규화하지 않는다.

```python
# inventory.py:196
slot = groups.setdefault(series_of(f.stem), {})
```

`series_of(f.stem)` 은 파일 시스템이 준 이름을 그대로 쓴다. 한 폴더 안에
`그렌라간01.mp4`(NFC)와 `그렌라간02.mp4`(NFD)가 함께 있으면 — exFAT·ext4·SMB 볼륨에서
가능하다(§31.3) — 줄기가 **다른 두 키**가 되어 무리가 둘로 갈린다.

그 뒤 `stock_for` 가 `_key` 로 정규화하면 두 키가 **같아진다.** 그러면 완전 일치
후보든 포함 후보든 둘이 되어 길이 우열이 생기지 않는다. 코드는 모호하다고
판단해 포기한다([`inventory.py:253-256`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L253-L256)). 실제 코드로 재현한 결과다.

```
$ python3 -c "
import unicodedata as u, sys; sys.path.insert(0,'.')
from hlsrecon import inventory
from hlsrecon.inventory import Item
from pathlib import Path
nfc, nfd = u.normalize('NFC','그렌라간'), u.normalize('NFD','그렌라간')
groups = {nfc: {1: Item(1, Path(nfc+'01.mp4'))},
          nfd: {2: Item(2, Path(nfd+'02.mp4'))}}
stock, note = inventory.stock_for(groups, '천원돌파 그렌라간')
print(len(stock), note)
"
0 작품명과 맞는 무리가 여럿이다 (그렌라간, 그렌라간) — 번호로 가릴 수 없다
```

**사용자에게 보이는 진단 메시지가 `(그렌라간, 그렌라간)` 이다.** 두 이름이 똑같이
보이므로 이 메시지를 받은 사람은 무엇이 잘못됐는지 알아낼 방법이 없다. §31.1 의
문제가 오류 메시지 안에서 한 번 더 재생된다.

정리하면 이 코드의 정규화 배치는 이렇다.

| 지점 | 정규화 | 결과 |
|---|---|---|
| `sanitize` — 쓰기 직전 | **함** | 이 도구가 만드는 이름은 항상 NFC |
| `_key` — 견주기 직전 | **함** | 표기가 달라도 같은 작품으로 인식 |
| `series_of` — 무리로 묶을 때 | **안 함** | 표기가 다르면 무리가 갈린다 |

셋째 줄이 미해결이다. 고치는 방법은 §31.8 에 적는다.

### 31.5.3 회귀 테스트는 이것을 고정하지 못한다

재고 조사 검증은 실제 파일을 만들어 실제 코드를 돌린다(`tests/run.sh:366-397`).

```bash
# tests/run.sh:372-373
groups = inventory.scan(folder)
stock, note = inventory.stock_for(groups, "천원돌파 그렌라간")
```

그리고 결과를 아홉 개 단언으로 못박는다(`tests/run.sh:399-417`). 그중 `_key` 를 실제로
거치는 것은 `MIXED`·`ALONE` 둘뿐이다 — `NOTE` 단언(`tests/run.sh:411-413`)이 보는
폴더는 무리가 하나뿐이라 `stock_for` 의 이른 반환([`inventory.py:234-236`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L234-L236))에 걸린다.
정규화와 가장 가까운 것이 이것이다.

```bash
# tests/run.sh:416-417
grep -q 'ALONE 2' "$INV" \
  && ok "한 무리에만 걸리면 가려낸다 (--flat 에서도 동작)" || bad "가릴 수 있는데도 포기함"
```

**이 단언은 `_key` 의 포함 판정을 고정하지만 NFC 변환은 고정하지 못한다.**
이유는 측정으로 확인했다.

- `tests/run.sh` 소스의 한글 조각 1,187개가 **전부 NFC** 다 (NFD 조각은 0개).
- 셸이 그 NFC 이름으로 파일을 만들고, APFS 는 표기를 보존한다(§31.3).
- 따라서 `inventory.scan` 이 읽어오는 이름도 **NFC** 다.

즉 이 테스트가 도는 동안 `unicodedata.normalize("NFC", s)` 는 **항상 항등 함수**다.
정규화 호출을 통째로 지워도 62개 테스트가 전부 통과한다.

이것은 테스트의 결함이라기보다 **테스트가 도는 환경이 그 결함을 드러내지 못하는
경우**다. 제34장(테스트 오라클 문제)의 표현을 빌리면, 이 검사의 PASS 는
"NFC 변환이 옳다"가 아니라 "이 볼륨에서는 NFC 변환이 필요 없었다"를 뜻한다.
고정하려면 **파일을 만드는 쪽이 NFD 이름을 명시적으로 써야 한다** — §31.8 참조.

## 31.6 일반화 — 변환은 경계에서 한 번

이 장의 두 지점(`sanitize`·`_key`)이 공유하는 형태를 뽑으면 이렇다.

> **표현을 바꾸는 변환은 시스템의 경계에서 한 번만 하고, 그 안쪽은 한 가지 표현만
> 다룬다.**

경계는 둘이다 — **들어올 때**(외부 표현 → 내부 표준형)와 **나갈 때**(내부 표준형 →
외부 표현). 안쪽에서 다시 변환하면 두 문제가 생긴다.

| 문제 | 무슨 일이 벌어지는가 |
|---|---|
| **멱등성 붕괴** | 변환이 멱등이 아니면(예: 퍼센트 인코딩) 두 번 걸린 값이 다른 값이 된다 → 제7장 `%20` → `%2520` |
| **검증-사용 괴리** | 검증한 값과 실제로 쓰이는 값이 달라진다 → §31.7 |

같은 구조가 이 도메인 밖 어디에 나타나는지 나열하면 다음과 같다.

| 영역 | 외부 표현 | 내부 표준형 | 변환 지점 |
|---|---|---|---|
| **유니코드 문자열** | NFC · NFD 혼재 | NFC (또는 NFD) | 입력 경계 (이 장) |
| **URL** | `%20` · `+` · 대소문자 혼재 스킴 | 정규화된 URL | `fetch.normalize_url` (제7장) |
| **시각** | 지역 시각 · 오프셋 표기 | UTC 정수 | 파싱 경계 |
| **개행** | CRLF · CR · LF | LF | 파일 읽기 경계 |
| **경로** | 상대 경로 · 심볼릭 링크 · `..` | 절대 실경로 | `Path.resolve()` (`tests/gzip_server.py:22-25`) |
| **부동소수** | 십진 문자열 | 이진 배정도 | 파싱 경계 |
| **이메일 주소** | 대소문자 · 점 변형 | 서비스가 정한 표준형 | 가입·로그인 경계 |

각 행에서 "변환 지점"이 여럿으로 흩어진 시스템은 모두 같은 방식으로 고장 났다.
그리고 **표준형을 무엇으로 잡느냐는 대개 임의 선택이지만, 하나로 정하지 않는 것은
임의 선택이 아니라 결함이다.**

이 저장소가 NFD 가 아니라 NFC 를 표준형으로 고른 이유도 그 임의성의 범위 안에 있다.
NFC 가 짧고(한글 12바이트 vs 30바이트), 웹에서 오는 값이 이미 대개 NFC 이며,
W3C 가 웹 콘텐츠에 NFC 를 권고하므로 변환 횟수가 줄어든다. **NFD 로 통일했어도
정확성은 같다.** 정해진 것이 하나라는 사실이 중요하지 어느 쪽인지는 덜 중요하다.

## 31.7 보안 — 유니코드 정규화 공격

### 31.7.1 구조 — 정규화 시점과 검증 시점의 어긋남

정규화의 정의를 공격자 관점으로 뒤집어 읽으면 이렇게 된다.

> **정규화는 서로 다른 문자열을 같은 문자열로 만드는 함수다.**

방어 측에서 이 성질은 "표기가 달라도 같은 것으로 인식한다"는 편의다. 공격 측에서
같은 성질은 "검증기를 통과하는 표기를 찾을 수 있다"는 뜻이다. 둘을 가르는 것은
성질 자체가 아니라 **순서**다.

![검증과 정규화의 순서가 우회를 만든다](/images/lecture/hls-recon/31-normalize-then-validate.svg)

*그림 31-2 — 검증과 정규화의 순서가 우회를 만든다*

> **용어** — **유니코드 정규화 공격(Unicode normalization attack)**: 검증을 통과하는
> 표기로 입력을 넣은 뒤, 검증 **이후**의 정규화가 그것을 금지된 값으로 바꾸게 하는
> 공격. 더 넓게는 **정준화 공격(canonicalization attack)** 의 한 종류이며,
> CWE-180(Incorrect Behavior Order: Validate Before Canonicalize)으로 분류된다.

공격이 성립하는 조건은 셋이고, 셋이 다 필요하다.

| 조건 | 내용 |
|---|---|
| ① | 입력이 검증을 거친다 |
| ② | 검증 **이후에** 문자열을 바꾸는 단계가 있다 (정규화·접기·인코딩 변환) |
| ③ | 그 변환이 검증이 막으려던 값을 **만들어낼 수 있다** |

③이 핵심이다. 변환이 문자열을 바꾸기만 해서는 부족하고, **금지 목록에 있는 값으로**
바꿔야 한다. 그런 코드포인트가 실제로 몇 개나 되는지는 셀 수 있다 — §31.7.3.

### 31.7.2 "우리는 NFC 만 쓴다"는 방어가 되지 못한다

§31.2.3 의 정준 특이 분해가 여기서 값을 한다. 실측한 결과다.

```
raw  'Key'    cp = U+212A U+0065 U+0079      ← 첫 글자가 KELVIN SIGN
NFC           cp = U+004B U+0065 U+0079      ← ASCII 'Key'
NFC.casefold  cp = U+006B U+0065 U+0079      ← ASCII 'key'
```

`U+212A` 는 ASCII 가 아니고, 바이트 열로도 `K` 와 전혀 다르다. **ASCII 문자열 `"Key"`
를 찾는 어떤 검사도 이것을 잡지 못한다.** 그런데 NFC 한 번이면 ASCII 가 된다.

`casefold` 도 같은 성질을 가진다.

```
raw           'adminiſtrator'   ← 7번째가 U+017F LATIN SMALL LETTER LONG S
NFC           'adminiſtrator'   ← NFC 는 건드리지 않는다
NFC.casefold  'administrator'   ← 접기가 ſ 를 s 로 만든다
```

여기서 실무 원칙이 나온다.

> **"위험한 정규화(NFKC)만 피하면 된다"는 판단은 틀렸다. 문자열을 바꾸는 모든
> 단계가 조건 ②에 해당한다** — NFC 도, `casefold()` 도, `lower()` 도, 인코딩 왕복도.

### 31.7.3 NFKC 는 예약 문자를 **만들어낸다** — 셀 수 있다

호환 정규화는 서식 문자를 ASCII 로 편다. 그 ASCII 중에 구분자가 들어 있다.
[`naming.py:26`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/naming.py#L26) 의 예약 문자 집합을 그대로 써서 유니코드 전 코드포인트를 훑었다.

```python
# naming.py:26
_UNSAFE_RE = re.compile(r'[/\\:*?"<>|\x00-\x1f]')
```

**"원래는 예약 문자가 아니었는데 정규화 결과에 예약 문자가 섞이는" 코드포인트의 수**다.

| 형식 | 해당 코드포인트 수 | 예 |
|---|---|---|
| **NFC** | **0개** | — |
| NFD | 2개 | `≮` U+226E → `<`(U+003C) + `◌̸`(U+0338) |
| **NFKC** | **25개** | `℀` U+2100 → `a/c` · `︓` U+FE13 → `:` · `？` U+FF1F → `?` |
| NFKD | 27개 | 위 둘의 합집합 |

이 표가 `sanitize` 의 두 결정을 동시에 정당화한다.

**첫째, NFC 를 고른 것.** NFC 로는 예약 문자가 만들어지는 경우가 **0개**다. 만약
호환 정규화를 썼다면 `℀`(ACCOUNT OF) 한 글자가 `a/c` 세 글자가 되어 **파일 이름
안에 경로 구분자가 생긴다.** 검증이 통과시킨 것은 예약 문자 없는 이름 하나였는데,
실제로 만들어지는 것은 `a` 폴더 아래 `c` 파일이다.

**둘째, 순서.** 현재 코드는 정규화를 먼저 하고 치환을 나중에 한다.

```python
# naming.py:128
s = _UNSAFE_RE.sub("_", unicodedata.normalize("NFC", name)).strip()
```

순서를 뒤집으면(`normalize(NFC, _UNSAFE_RE.sub(...))`) 조건 ①②③이 그대로 성립한다.
NFC 에 한해서는 위 표의 0개 때문에 결과가 우연히 같지만, **누군가 NFKC 로 바꾸는
순간 조용히 취약해진다.** 실측으로 그 차이를 확인했다.

```
$ python3 -c "
import unicodedata as u, sys; sys.path.insert(0,'.')
from hlsrecon.naming import sanitize
print(repr(sanitize('a／b')))                     # 현재 코드 (NFC)
print(repr(u.normalize('NFKC', 'a／b')))          # 호환 정규화였다면
"
'a／b'
'a/b'
```

위는 전각 솔리더스가 그대로 남아 **평범한 파일 이름 한 개**이고, 아래는 ASCII
슬래시가 되어 **경로 두 조각**이다. 같은 입력, 다른 정규화 형식, 다른 신뢰 경계.

> **이 저장소의 코드가 안전한 이유는 순서가 옳아서가 아니라 NFC 를 골랐기
> 때문이다.** 순서는 지금 우연히 안전하다. 이것은 제15장이 "우연한 방어(incidental
> defense)" 라고 이름 붙인 상태와 같은 형태다 — 다른 결정이 앞을 막고 있어서 이
> 결정의 옳고 그름이 관측되지 않는다.

### 31.7.4 같은 구조가 나타나는 곳

정규화 공격의 고전적 벡터들을 조건 ①②③에 맞춰 정리하면 이렇다. 모두 널리 문서화된
취약점 유형이며, 특정 서비스를 겨냥한 절차가 아니라 **패턴**으로 적는다.

| 벡터 | ① 검증이 막으려던 것 | ② 이후의 변환 | ③ 만들어지는 값 |
|---|---|---|---|
| **경로 순회** | `../` | NFKC · 인코딩 변환 | 전각 `．．／` → `../` |
| **인증 우회** | 이미 존재하는 계정명 | NFC · `casefold` · `lower` | `ſ`→`s`, `U+212A`→`K` 로 기존 계정과 충돌 |
| **XSS 필터 우회** | `<` `>` | NFKC | `﹤` U+FE64 → `<` |
| **SQL 주입 필터 우회** | `'` `"` | NFKC · 인코딩 변환 | 전각 따옴표 → ASCII 따옴표 |
| **길이 제한 우회** | 최대 N자 | NFD (길어짐) · NFKC (짧아짐) | 4자가 10자로, `½` 가 `1⁄2` 로 |
| **중복 계정 생성** | 기존과 같은 이름 | 저장 시에만 정규화 | 등록은 통과, 조회는 충돌 |

마지막 행이 흥미롭다. **정규화를 아예 안 해도 문제이고(중복 계정), 검증 뒤에 하면
문제다(인증 우회).** 안전한 지점은 하나뿐이다 — **검증보다 먼저, 그리고 한 번만.**

두 번째 행이 인증 우회의 표준적 형태다. 신규 가입 시 "이미 있는 이름"을 원본
문자열로 검사하고, 저장할 때 정규화하면, 정규화 후 기존 계정과 같아지는 이름으로
가입할 수 있다. 그 뒤 조회가 정규화된 키로 이루어지면 두 계정이 하나로 접힌다.
막는 방법은 §31.7.5 에 적는다.

### 31.7.5 방어자 관점

| 역할 | 해야 할 일 |
|---|---|
| **입력을 받는 쪽** | **정규화를 검증보다 먼저** 한다. 그리고 정규화한 값을 이후 단계에 넘긴다 — 원본을 넘기면 순서가 옳아도 소용이 없다 |
| **계정·식별자를 다루는 쪽** | 저장 시 정규화된 키를 **함께 저장하고 그 키에 유일 제약(unique constraint)을 건다.** 검사와 저장이 같은 키를 쓰면 §31.7.4 의 여섯 벡터가 한꺼번에 닫힌다 |
| **필터·차단 목록을 만드는 쪽** | 금지 문자열 목록도 **같은 정규화를 거친 형태**로 둔다. 입력만 정규화하고 목록은 원본이면 매칭이 어긋난다 |
| **API 를 설계하는 쪽** | 정규화 형식을 **문서에 명시**한다. "NFC 로 정규화된 UTF-8" 같은 문장 한 줄이 없으면 클라이언트마다 다른 형식을 보낸다 |
| **감사자** | 코드에서 `normalize`·`casefold`·`lower`·`decode` 호출 위치를 전부 뽑고, **각 호출이 검증보다 앞인지 뒤인지**를 표로 만든다. 뒤에 있는 것이 곧 후보다 |
| **파일 이름을 만드는 쪽** | 정준 정규화(NFC/NFD)를 쓰고 호환 정규화(NFKC/NFKD)는 쓰지 않는다. 호환 정규화는 §31.7.3 의 25개 코드포인트로 구분자를 만들어낸다 |

두 번째 행이 가장 효과가 크다. **"검사와 저장이 같은 키를 쓴다"는 것은 검증 시점과
정규화 시점을 어긋나게 할 여지 자체를 없애는 설계**다. 순서를 지키라고 요구하는 것보다
순서를 틀릴 수 없게 만드는 편이 낫다.

### 31.7.6 동형 문자는 다른 문제다 — 이 코드의 범위 밖

정규화 공격과 자주 묶여 이야기되지만 **정규화로는 해결되지 않는** 문제가 있다.

> **용어** — **동형 문자(homoglyph)**: 서로 다른 문자인데 글꼴에서 거의 같게 보이는
> 문자. 라틴 `a`(U+0061)와 키릴 `а`(U+0430)가 대표적이다. 유니코드는 이 관계를
> **혼동 가능(confusable)** 이라 부르고 UTS #39(Unicode Security Mechanisms)에서
> 별도로 다룬다.

정규화는 이것을 통합하지 않는다. 확인했다.

```
NFC : 라틴 a == 키릴 а ?  False
NFD : 라틴 a == 키릴 а ?  False
NFKC: 라틴 a == 키릴 а ?  False
NFKD: 라틴 a == 키릴 а ?  False
casefold 를 더해도       False
```

**네 형식 모두 거짓이다.** 이유는 §31.2.1 의 정의에 있다 — 둘은 정준 동치도 호환
동치도 아니다. **서로 다른 언어의 서로 다른 문자**이고, 유니코드가 그것을 통합하면
키릴 텍스트가 망가진다. 즉 이것은 정규화의 실패가 아니라 **정규화의 범위 밖**이다.

| 문제 | 관계 | 해결 수단 |
|---|---|---|
| NFC ↔ NFD | 정준 동치 | **정규화** (이 장) |
| `ﬁ` ↔ `fi` | 호환 동치 | 정규화 (NFKC) — 단, 정보 손실 |
| 라틴 `a` ↔ 키릴 `а` | **동치 아님** | UTS #39 혼동 가능 문자 탐지 (skeleton 알고리즘), 스크립트 혼용 제한 |

**이 저장소에는 동형 문자 대응이 없고, 있어야 할 이유도 없다.** 위협 모델이 다르기
때문이다. 이 코드가 견주는 두 문자열은 (a) 사용자 자신의 디스크에 있는 파일 이름과
(b) 사용자가 지정한 사이트가 알려준 작품명이다. **두 이름을 같아 보이게 만들어
이득을 얻는 주체가 없다.** 잘못 판정해도 결과는 "회차를 다시 받는다" 또는 "회차를
건너뛴다"이고, 후자는 코드가 모호할 때 포기하도록 설계해 막아 두었다.

동형 문자가 실제 위협이 되는 곳은 **이름이 곧 신원이거나 권한인 시스템**이다 —
도메인 이름(IDN 동형 공격), 계정명, 패키지 저장소의 패키지 이름, 코드 저장소의
조직 이름. 그런 시스템이라면 정규화만으로 부족하고 UTS #39 의 혼동 가능 문자 탐지와
스크립트 혼용 제한이 별도로 필요하다. **그것을 이 장의 정규화와 같은 문제로 묶으면
둘 다 틀리게 푼다.**

## 31.8 한계와 미해결

정직하게 적어 둔다.

- **코드 주석이 현재의 APFS 동작과 어긋난다.** [`naming.py:123`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/naming.py#L123) 과 [`inventory.py:208`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L208)
  의 "macOS 파일 시스템은 한글을 NFD 로 저장한다"는 서술은 HFS+ 기준이다. 이
  저장소의 작업 볼륨(APFS)에서 측정한 결과는 §31.3 과 같이 **표기 보존**이었다.
  정규화 코드가 필요하다는 결론은 그대로지만(§31.3 의 네 경로), **근거로 든 사실이
  오늘의 기본 파일 시스템에서는 성립하지 않는다.** 주석을 고치는 것이 옳다.

- **HFS+ 의 실제 동작을 이 환경에서 측정하지 못했다.** HFS+ 볼륨이 없어 확인할 수
  없었다. 문서상 HFS+ 는 순수 NFD 가 아니라 **일부 코드포인트 범위를 제외한 변종
  분해형**을 쓴다고 알려져 있으나, 그 범위를 직접 확인하지는 않았다. §31.3 표의
  HFS+ 행은 문헌에 근거한 것이지 실측이 아니다.

- **회귀 테스트가 NFC 변환을 고정하지 못한다**(§31.5.3). 측정으로 확인한 사실이다.
  `tests/run.sh` 의 한글 조각 1,187개가 전부 NFC 이고 APFS 가 표기를 보존하므로,
  테스트가 도는 동안 정규화 호출은 항등 함수다. 고치는 방법은 명확하다 — 테스트가
  파일을 만들 때 **NFD 이름을 하나 섞고**, 그 회차가 재고로 인식되는지 단언하면 된다.
  다만 그 단언은 **APFS 의 정규화 불변성 때문에 여전히 통과할 수 있으므로**,
  `_key` 를 직접 호출하는 단위 검사를 함께 두는 편이 확실하다. 이 장은 그 변경을
  제안하되 적용하지 않았다.

- **`series_of` 의 그룹 키가 정규화되지 않는다**(§31.5.2). 재현 가능한 결함이다.
  고치려면 [`inventory.py:196`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/inventory.py#L196) 의 그룹 키를 정규화된 형태로 만들고 표시용 원본을
  따로 들고 있어야 한다. 이 장에서 코드를 바꾸지 않은 이유는 두 가지다 — (a) 표시용
  이름을 어느 것으로 고를지(먼저 만난 것 / NFC 로 고친 것)가 별도 결정이고,
  (b) 이 결함을 재현하는 회귀 테스트를 먼저 두어야 하는데 그것이 위 항목과 얽혀
  있다. **고칠 자리는 확정했고 고치지는 않았다.**

- **`_key` 는 유니코드 표준이 정의한 정확한 caseless matching 이 아니다.** 표준의
  정준 caseless 일치는 `NFD(casefold(NFD(x)))` 로 정규화를 두 번 건다. `_key` 는
  `NFC(x).casefold()` 로 한 번만 건다. 접기 결과가 다시 정규화되지 않는 문자가
  실제로 26개 존재함을 확인했다(예: U+0390 GREEK SMALL LETTER IOTA WITH DIALYTIKA
  AND TONOS). 다만 **단일 코드포인트 전 범위(0x0–0x10FFFF)를 훑어 표준 정의로는
  같은데 `_key` 로는 갈라지는 사례를 찾아보았고, 0개였다.** 여러 코드포인트로 이루어진
  문자열까지 전수 검사한 것은 아니므로, "이 코드에서는 차이가 관측되지 않았다"까지가
  검증된 범위다.

- **§31.7.4 의 벡터 표는 구조를 정리한 것이지 실증이 아니다.** 각 항목이 실제
  취약점으로 보고된 유형인 것은 문헌으로 확인되지만, 이 장에서 직접 재현한 것은
  §31.7.2·§31.7.3 의 문자열 변환 실측뿐이다. 어떤 시스템이 그 조건을 만족하는지는
  그 시스템을 열어 봐야 안다.

## 31.9 요약

1. **눈에 같은 두 문자열이 다를 수 있다.** 한글 `그렌라간` 은 NFC 로 4 코드포인트
   12바이트, NFD 로 10 코드포인트 30바이트다. `==` · `len()` · 정렬 · 해시가 전부
   다른 답을 낸다.
2. 유니코드는 같음을 두 층으로 정의한다 — **정준 동치**(같은 문자의 다른 표기)와
   **호환 동치**(다른 문자인데 뜻이 통함). 정규화 형식 넷은 이 두 동치와
   합성/분해의 조합이다. **정준(NFC/NFD)은 호환 문자를 건드리지 않는다.**
3. **파일 시스템의 동작은 볼륨에 달렸다.** HFS+ 는 분해형으로 바꿔 저장하고,
   APFS 는 표기를 보존하되 조회에서 형식을 무시하며, exFAT·ext4 는 바이트 그대로
   견준다. 마지막 부류에서만 두 표기가 **공존**할 수 있다.
4. 이 코드는 NFC 로 고정하는 지점을 **둘**만 둔다 — 쓰기 직전(`sanitize`)과
   견주기 직전(`_key`). 앞의 것은 **되돌릴 수 있어야** 하므로 정준 정규화만 하고,
   뒤의 것은 **버릴 값**이므로 구분자 제거와 `casefold` 까지 더한다.
5. `casefold` 는 `lower` 와 다르다. `ß`→`ss`, `ſ`→`s`, `ﬁ`→`fi` 로 **길이까지
   바꾸는 비교 전용 연산**이다. 한글에서는 항등이지만, 비교 키를 만드는 자리에는
   `casefold` 가 옳다.
6. 정규화를 빼면 **이미 받아둔 27화를 못 알아보고 전부 다시 받는다.** 그리고 이
   코드는 아직 `series_of` 의 그룹 키를 정규화하지 않아, 한 폴더에 두 표기가 공존하면
   `(그렌라간, 그렌라간)` 이라는 **읽을 수 없는 진단 메시지**를 내고 포기한다.
7. **정규화는 서로 다른 문자열을 같게 만드는 함수다.** 이 성질이 검증 **이후에**
   작동하면 우회가 된다(CWE-180). 조건은 셋 — 검증이 있고, 그 뒤에 변환이 있고,
   그 변환이 금지된 값을 만들어낼 수 있다.
8. **"NFKC 만 피하면 된다"는 틀렸다.** `U+212A KELVIN SIGN` 은 **NFC 만으로**
   ASCII `K` 가 되고, `ſ` 는 `casefold` 만으로 `s` 가 된다. 문자열을 바꾸는 모든
   단계가 위험 구간이다.
9. 다만 **파일 이름 생성에서는 형식 선택이 결정적이다.** 예약 문자를 만들어내는
   코드포인트가 NFC 는 **0개**, NFKC 는 **25개**다(`℀`→`a/c`, `︓`→`:`).
   이 코드가 안전한 것은 순서 때문이 아니라 NFC 를 고른 덕이다 — 순서는 지금
   **우연히** 안전하다.
10. **동형 문자는 정규화의 문제가 아니다.** 라틴 `a` 와 키릴 `а` 는 네 형식 어느
    쪽으로도 같아지지 않으며, 같아져서도 안 된다. UTS #39 의 혼동 가능 문자 탐지가
    별도로 필요하고, **이 저장소의 위협 모델에는 그것이 들어 있지 않다.**
