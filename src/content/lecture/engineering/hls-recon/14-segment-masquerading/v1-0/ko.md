## 14.0 이 장에서 답할 것

1. 영상 세그먼트가 `.html` 로 오는 송출은 무엇을 하는 것인가
2. 그것은 HLS 규격 위반인가
3. 왜 그렇게 보내는가
4. 받는 쪽은 무엇을 근거로 판별해야 하는가

---

## 14.1 문제 — 관찰

어떤 스트리밍 사이트를 개발자도구로 열어 보면 영상 세그먼트 요청이 이렇게 나간다.

```
GET /hls/9f3a…/1080p_010.html
→ 200 OK
   Content-Type: text/html
   Content-Length: 1128368
```

`.html` 이고, `text/html` 이고, 1.1 MB 다. 여기서 자연스러운 추측 둘이 갈린다.

- **추측 A**: HTML 안에 영상 데이터를 담아 보낸다 (base64 인코딩 등)
- **추측 B**: HTML 은 이름뿐이고 내용은 영상이다

둘을 가르는 방법은 하나뿐이다 — **본문의 선두 바이트를 직접 보는 것.**

```
$ xxd -l 4 seg000.html
00000000: 4740 1110                                G@..
```

`0x47` 이다. 이것은 **MPEG-TS 의 동기 바이트(sync byte)** — MPEG-2 Transport Stream 의
188바이트 패킷마다 선두에 오는 고정값이다. 추측 B 가 맞다.

**HTML 은 어디에도 없다.** 파싱될 태그도, `<html>` 도, base64 문자열도 없다. 파일명
확장자와 응답 헤더의 `Content-Type` 만 HTML 이라고 주장하고 있고, 실제 바이트열은
평범한 MPEG-TS 다.

이 관행의 정확한 명칭은 **콘텐츠 타입 위장(content-type masquerading)** 이다.
"HTML 로 스트리밍한다"는 표현은 두 번 틀렸다 — HTML 이 쓰이지 않고, 스트리밍
프로토콜이 바뀌지도 않았다. 전송은 여전히 **평범한 HTTP GET** 이다. 웹소켓도,
별도 프로토콜도 관여하지 않는다.

## 14.2 원리 — 파일에는 세 개의 이름이 있다

이 현상을 이해하려면 "이 자원이 무엇인가"를 말하는 층이 하나가 아니라는 사실부터
분리해야 한다.

![하나의 세그먼트 응답에서 자원의 정체를 말하는 세 층위](/images/lecture/hls-recon/14-three-names.svg)

*그림 14-1 — 하나의 세그먼트 응답에서 자원의 정체를 말하는 세 층위*

①과 ②는 **서버의 자기 신고(self-reported)** 값이다. 어떤 규격도 이것이 참임을
강제하지 않으며, 강제할 방법도 없다. 반면 ③은 위조할 수 없다 — 위조하면 그 순간
영상이 재생되지 않기 때문이다. **송출자에게도 ③만은 바꿀 수 없다는 제약이 있고,
그것이 받는 쪽의 유일한 지렛대가 된다.**

위장 송출은 ①·②만 바꾸고 ③은 건드리지 않는다. 그것이 이 관행이 성립하는 조건
전체다.

> **용어** — **매직 넘버(magic number)**: 파일 형식을 식별하기 위해 선두에 놓이는
> 고정 바이트열. MPEG-TS 는 `0x47` 이 188바이트 주기로 반복되고, ISO-BMFF(MP4 계열)는
> 오프셋 4–8 에 박스 타입(`ftyp`·`styp`·`moof` 등)이 온다.

## 14.3 규격은 무엇을 요구하는가

### 14.3.1 RFC 8216 은 세그먼트 확장자를 규정하지 않는다

RFC 8216(HTTP Live Streaming)이 확장자에 대해 MUST 를 두는 대상은 **플레이리스트뿐**
이다. 플레이리스트는 경로가 `.m3u8`/`.m3u` 로 끝나거나 Content-Type 이
`application/vnd.apple.mpegurl`(또는 `audio/mpegurl`)이어야 한다.

**미디어 세그먼트에 대해서는 그런 요구가 없다.** 규격이 요구하는 것은 세그먼트의
*포맷*(MPEG-TS · ISO-BMFF 등)이지 *이름*이나 *선언된 타입*이 아니다.

![RFC 8216 이 확장자·타입에 요구를 두는 대상](/images/lecture/hls-recon/14-rfc-scope.svg)

*그림 14-2 — RFC 8216 이 확장자·타입에 요구를 두는 대상*

이 저장소의 파서도 같은 구분을 코드에 그대로 반영하고 있다.

```python
# playlist.py:18-24
def is_playlist_uri(uri: str) -> bool:
    """주소가 플레이리스트를 가리키는가 — 경로 확장자로만 판단한다.

    자막 트랙 URI 에 자막 플레이리스트 대신 완성된 `.srt` 를 넣는 송출이 있어,
    받아보기 전에 갈라내야 하는 자리가 생긴다.
    """
    return urlsplit(uri).path.lower().endswith(PLAYLIST_SUFFIXES)
```

확장자로 판단하는 대상이 **플레이리스트에 한정**되어 있다는 점이 중요하다. 세그먼트를
같은 방식으로 판단하는 코드는 이 저장소 어디에도 없다.

### 14.3.2 그러나 HTTP 규격 위반이다

`Content-Type` 은 HTTP 규격상 전송되는 **표현의 실제 미디어 타입**을 나타내야 한다.
MPEG-TS 바이트열을 `text/html` 로 선언하는 것은 이 요구를 어긴다.

정리하면 이 관행은 다음 조합이다.

| 규격 | 판정 |
|---|---|
| RFC 8216 (HLS) | 위반 아님 — 세그먼트 URI 는 자유 |
| HTTP (Content-Type 정확성) | **위반** |

따라서 "정식 스트리밍 통신 방법"이라고 부를 근거는 없다. **HLS 규격의 빈틈을
이용하면서 HTTP 규격을 위반하는 회피 관행**이다.

### 14.3.3 그럼에도 사실상 인정되고 있다

규격 외 관행임에도 이것은 주변부 현상이 아니다. FFmpeg 8.1.1 의 HLS demuxer 기본값을
직접 조회하면 다음과 같다.

```
$ ffmpeg -h demuxer=hls | grep allowed_segment_extensions
-allowed_segment_extensions <string>  (default "3gp,aac,avi,ac3,eac3,flac,mkv,
  m3u8,m4a,m4s,m4v,mpg,mov,mp2,mp3,mp4,mpeg,mpegts,ogg,ogv,oga,ts,vob,vtt,
  wav,webvtt,cmfv,cmfa,ec3,fmp4,html")
                                                                    ↑
```

`html` 이 **세그먼트 허용 목록의 기본값에 들어 있다.** 비교 대상인 `allowed_extensions`
기본값에는 없다 — 세그먼트 전용 목록에만 있다.

이는 우연이 아니라 상류의 판단이다. **"세그먼트가 `.html` 로 오는 송출이 실재하므로,
재생하려면 허용해야 한다."** 반면 `.txt` 는 배제되어 있고 앞으로도 추가하지 않겠다는
방침이 공개 이슈로 확인된다. 즉 상류는 위장 확장자마다 개별 판단을 내리고 있으며,
`.html` 은 그중 인정받은 쪽이다.

## 14.4 코드 — 이 저장소는 어떻게 다루는가

### 14.4.1 판별은 헤더가 아니라 바이트로

```python
# tsanalyze.py:20-37
def sniff(data: bytes) -> str:
    """세그먼트 바이트의 컨테이너 종류를 판별한다: mpegts | fmp4 | unknown.

    HTTP 200 으로 응답했다고 미디어가 온 것은 아니다. …
    상태 코드가 아니라 선두 바이트로 판정한다.
    """
    if len(data) < 8:
        return "unknown"
    # TS 는 188바이트 주기로 sync byte 가 반복되므로 두 번째 패킷까지 확인한다.
    if data[0] == SYNC_BYTE and (
        len(data) < PACKET_SIZE + 1 or data[PACKET_SIZE] == SYNC_BYTE
    ):
        return "mpegts"
    if data[4:8] in _MP4_BOXES:
        return "fmp4"
    return "unknown"
```

이 함수는 `Content-Type` 도 상태 코드도 참조하지 않는다. 인자로 받지도 않는다 —
**받을 수 없게 만들어 두면 실수로 참조할 수도 없다.**

두 번째 패킷까지 확인하는 이유는 우연 일치 배제다. 임의의 바이트열이 `0x47` 로
시작할 확률은 1/256 이지만, 188바이트 뒤에도 `0x47` 일 확률은 1/65536 로 떨어진다.

### 14.4.2 판별 실패를 검사 항목으로 승격

```python
# cli.py:459-464
kind = sniff(data)
if kind == "unknown":
    # 200 을 받았지만 미디어가 아니다 — 오류 페이지가 실려 온 경우다.
    bogus.append((seg.index, res.content_type, data[:16].hex()))
    _eprint(f"    ✗ seg#{seg.index} 미디어가 아님 (Content-Type: {res.content_type or '없음'})")
    continue
```

판별 실패가 조용히 넘어가지 않고 `bogus` 목록에 쌓여 리포트의 **페이로드 유효성**
검사(FAIL)로 이어진다([`report.py:198-211`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/report.py#L198-L211)). 기록에 `Content-Type` 을 남기는 것은
판정 근거가 아니라 사후 분석용이다 — 어떤 CDN 이 무엇으로 선언했는지가 남는다.

### 14.4.3 ffmpeg 에 위임하는 경로에서는 인자가 필요하다

```python
# probe.py:79-80
if playlist.is_playlist_uri(target):
    args += ["-allowed_extensions", ALLOWED_SEGMENT_EXTS]
```

세그먼트를 직접 받는 경로(`segments` 모드)는 위 `sniff()` 로 충분하지만, 플레이리스트
URL 을 ffmpeg 에 통째로 넘기는 경로(`remux` 모드·`probe` 실측·자막 추출)는 ffmpeg 의
확장자 정책을 그대로 상속한다. 그 정책을 조정하는 것이 이 인자다.

`is_playlist_uri(target)` 조건이 붙은 이유는 별개의 실측 사례다 — 이 옵션은 HLS
demuxer 에만 존재하므로, 플레이리스트가 아닌 입력(자막 트랙에 완성 `.srt` 를 넣는
송출)에 붙이면 `Option allowed_extensions not found` 로 **열기 자체가 실패한다**
([`probe.py:70-73`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/probe.py#L70-L73)).

이 인자의 값이 왜 `ALL` 이 아니라 열거인지, 그리고 그 선택이 무엇을 얻고 무엇을 얻지
못했는지는 제15장에서 다룬다.

## 14.5 실습 — 로컬 재현

외부 사이트 없이 전 과정을 재현할 수 있다. 필요한 것은 `ffmpeg` 와 `python3` 뿐이다.

### 14.5.1 위장 스트림 만들기

```bash
# 5초짜리 테스트 패턴 HLS 스트림
ffmpeg -v error -y -f lavfi -i "testsrc2=size=320x180:rate=30:duration=5" \
  -f lavfi -i "sine=frequency=440:duration=5" \
  -c:v libx264 -preset ultrafast -g 30 -c:a aac \
  -f hls -hls_time 2 -hls_playlist_type vod \
  -hls_segment_filename "seg%03d.ts" index.m3u8

# 확장자만 바꾼 사본 — 내용은 손대지 않는다
mkdir -p as_html
for f in seg*.ts; do cp "$f" "as_html/${f%.ts}.html"; done
sed 's/\.ts$/.html/' index.m3u8 > as_html/index.m3u8
```

### 14.5.2 내용이 바뀌지 않았음을 확인

```bash
$ xxd -l 4 as_html/seg000.html
00000000: 4740 1110                                G@..
```

`0x47` — 확장자는 `.html` 이지만 MPEG-TS 다. **§14.2 의 ①만 바뀌고 ③은 그대로**임을
눈으로 확인하는 단계다.

### 14.5.3 확장자별 재생 가능 여부 측정

```bash
python3 -m http.server 8977 --bind 127.0.0.1 &
for ext in ts html txt png jpg aaa; do
  # (각 확장자로 사본을 만든 뒤)
  ffmpeg -v error -i "http://127.0.0.1:8977/as_$ext/index.m3u8" -c copy -f null -
done
```

측정 결과(ffmpeg 8.1.1, 원격 HTTP, 옵션 없음):

| `.ts` | `.html` | `.txt` | `.png` | `.jpg` | `.aaa` |
|---|---|---|---|---|---|
| 열림 | **열림** | 거부 | 거부 | 거부 | 거부 |

내용이 전부 동일한 MPEG-TS 인데도 결과가 갈린다. **파일명 하나가 재생 가능 여부를
결정한다** — 이것이 §14.2 에서 말한 "①과 ②는 아무것도 보증하지 않는다"의 반대편
귀결이다. 보증하지 않으면서도 **관문 역할은 한다.**

### 14.5.4 이 저장소 도구의 반응

같은 `.txt` 위장 스트림을 `hls-recon` 에 물리면 모드에 따라 결과가 갈린다.

| 모드 | 결과 |
|---|---|
| `--mode segments` | **성공** — 7개 검사 통과 |
| `--mode remux` | **실패** (ffmpeg exit 1) |

![같은 위장 스트림에서 갈라지는 두 경로](/images/lecture/hls-recon/14-mode-asymmetry.svg)

*그림 14-3 — 같은 위장 스트림에서 갈라지는 두 경로*

**위임에는 대가가 있다 — 위임받은 쪽의 정책까지 함께 상속한다.** [`assemble.py:1-6`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/assemble.py#L1-L6) 이
선언한 "컨테이너 작업은 전부 ffmpeg 에 위임한다"는 원칙의 구체적 귀결이다.

여기에 재현 난이도의 함정이 하나 겹친다. `auto` 모드([`cli.py:391-402`](https://github.com/hwanyong/hls-recon/blob/910c5a1f23676cdad3ce2c55f65eae37cc2b2a19/hlsrecon/cli.py#L391-L402))는 LIVE 이거나
세그먼트 단위 복호화가 불가능할 때만 `remux` 로 내려간다. 따라서 이 실패는
**LIVE + 위장 확장자** 조합에서만 나타나고, VOD 로 테스트하면 영원히 보이지 않는다.

## 14.6 일반화 — 이름과 내용의 분리

이 장의 원리는 스트리밍에 한정되지 않는다.

> **자기 신고 메타데이터는 편의를 위한 것이지 판단의 근거가 아니다.**

같은 구조가 나타나는 곳을 나열하면 다음과 같다.

| 영역 | 자기 신고 값 | 실제 근거 |
|---|---|---|
| 파일 업로드 | 파일명 확장자, `Content-Type` | 매직 넘버, 실제 파싱 결과 |
| 이메일 첨부 | 첨부 파일명, MIME 파트 선언 | 페이로드 검사 |
| 패키지 저장소 | 패키지 메타데이터의 이름·버전 | 서명, 해시 |
| HTTP 인증 | `X-Forwarded-For`, `Referer`, `User-Agent` | 없음 — 위조 가능 |
| 컨테이너 이미지 | 태그 이름 | 다이제스트(digest) |

각 행에서 왼쪽 열을 근거로 삼은 시스템은 모두 같은 방식으로 우회당했다. 파일 업로드가
확장자만 검사하면 웹셸이 올라가고, `X-Forwarded-For` 로 IP 를 판단하면 접근 통제가
무너진다.

**이 장의 세그먼트 위장은 그 목록의 한 항목일 뿐이다.** 다만 특이한 점이 있다 —
여기서는 위장하는 쪽이 공격자가 아니라 **서비스 제공자 자신**이고, 위장을 뚫어야 하는
쪽이 정상 재생을 원하는 클라이언트다. 공격자와 방어자의 역할이 통상과 반대로 놓여
있다.

## 14.7 보안 — 왜 이렇게 보내는가

위장이 겨냥하는 것은 **URL 문자열과 응답 헤더만 보고 판단하는 모든 중간 계층**이다.

| 층위 | 회피 대상 | 작동 원리 |
|---|---|---|
| 클라이언트 확장 | 광고 차단기, 다운로드 확장 | 필터 목록이 `.ts`·`\.m3u8` 같은 URL 패턴을 쓴다 |
| 기업·학교 프록시 | 콘텐츠 필터, MIME 기반 차단 | "동영상 MIME 차단" 규칙이 `video/*` 를 보는데 `text/html` 은 걸리지 않는다 |
| 네트워크 장비 | DPI, 트래픽 셰이핑 | 확장자·MIME 으로 트래픽을 분류해 대역을 제한하는 장비를 통과 |
| 자동 수집기 | 소박한 스크래퍼 | `.ts` 를 찾아 도는 도구가 아무것도 찾지 못한다 |
| CDN·과금 | 캐시 정책, 대역 단가 | 일부 CDN 은 MIME 별로 캐시 규칙과 단가가 다르다 |

> **용어** — **DPI(Deep Packet Inspection, 심층 패킷 검사)**: 패킷의 헤더뿐 아니라
> 페이로드까지 들여다보아 트래픽 종류를 분류하는 기법.

다섯 층위가 공유하는 전제는 하나다.

> **"파일이 무엇인지는 이름과 선언이 말해 준다."**

위장은 이 전제 하나를 무너뜨려 다섯 층을 한꺼번에 통과한다. 그리고 **그 전제는
원래부터 참이 아니었다.** 위장이 새로운 취약점을 만든 것이 아니라, 처음부터 성립하지
않던 가정에 의존하던 통제가 드러난 것이다.

### 14.7.1 방어자 관점

| 방어자 | 판단 |
|---|---|
| **네트워크 관리자** | 확장자·MIME 은 **통제 지점이 될 수 없다.** 통제하려면 페이로드를 봐야 하고, 그러려면 TLS 종단이 필요하다. 즉 이 계층에서의 통제는 원리적으로 한계가 있다 |
| **광고 차단기 개발자** | URL 패턴 필터는 군비 경쟁이다. 지속 가능한 것은 동작 기반 탐지이지 문자열 매칭이 아니다 |
| **플랫폼 운영자** | 업로드·수신 경로에서 확장자를 신뢰하면 안 된다. 이 장의 원리가 방향만 바꿔 그대로 적용된다 |
| **송출 사업자** | 필터 회피를 얻는 대가로, 자사 콘텐츠를 여는 **모든 클라이언트에게 확장자 방어를 완화하도록 요구**하게 된다 → 제15장 |

### 14.7.2 같은 헤더, 정반대 의미

이 장의 마지막 층이다. 위장 송출을 다루는 클라이언트는 다음 두 응답을 구별해야 한다.

| 경우 | 상태 | Content-Type | 선두 바이트 | 실제 의미 |
|---|---|---|---|---|
| 위장된 정상 세그먼트 | `200` | `text/html` | `47 40 11 10` | **정상** — 그대로 처리해야 한다 |
| 토큰 만료 오류 페이지 | `200` | `text/html` | `3C 21 44 4F` (`<!DO`) | **실패** — FAIL 로 잡아야 한다 |

**헤더가 완전히 동일하다.** 상태 코드도, Content-Type 도 같다. 선두 바이트 외에는
구분 근거가 존재하지 않는다.

`README.md:247-250` 이 이 사실을 실측으로 기록해 두었다.

> `text/html` 이라고 선언된 정상 세그먼트를 오류 페이지로 오인하지 않고, 반대로 토큰
> 만료 시 오는 진짜 HTML 오류 페이지는 잡아낸다 — 이 CDN 에서는 둘의 헤더가 완전히
> 같아서 이 방식이 아니면 구분할 수 없다.

**이 판별을 하지 않는 도구는 오류 페이지를 세그먼트로 저장한 뒤 "전량 수신 성공"을
보고한다.** 검증 도구가 정반대의 결론을 내는 지점이며, 이 저장소의 회귀 테스트가
이 상황을 결함 주입으로 고정해 둔 이유다(`tests/run.sh:141-145`).

## 14.8 한계와 미해결

정직하게 적어 둔다.

- **동기의 비중은 추정이다.** §14.7 의 다섯 층위는 모두 기술적으로 성립하지만, 특정
  송출자가 실제로 어느 것을 노렸는지는 그 송출자만 안다.
- **`.html` 의 특별 대우는 상류 정책에 의존한다.** FFmpeg 이 기본 허용 목록에서
  `.html` 을 빼면 현재 동작이 바뀐다. 코드가 상류의 판단에 묶여 있는 지점이다.
- **`sniff()` 는 두 컨테이너만 안다.** MPEG-TS 와 ISO-BMFF 외의 세그먼트 포맷
  (예: 패킷화된 오디오)은 `unknown` 으로 떨어져 오탐이 된다. 현재 이 저장소가 다루는
  범위에서는 문제가 없지만 일반 도구라면 한계다.

## 14.9 요약

1. `.html` 세그먼트는 **HTML 이 아니다.** 확장자와 `Content-Type` 만 바뀌고 페이로드는
   MPEG-TS 그대로다. 전송도 평범한 HTTP GET 이며 별도 프로토콜이 없다.
2. **HLS 규격 위반은 아니다** — RFC 8216 은 세그먼트 URI 를 규정하지 않는다. 다만
   `Content-Type` 을 틀리게 선언하는 것은 **HTTP 규격 위반**이다.
3. 파일에는 세 개의 이름이 있다 — URI 확장자·Content-Type·페이로드. 앞의 둘은 서버의
   자기 신고이고 **아무것도 보증하지 않는다.** 위조할 수 없는 것은 셋째뿐이다.
4. FFmpeg 이 `.html` 을 세그먼트 허용 목록 기본값에 넣을 만큼 이 관행은 퍼져 있다.
5. **위임에는 정책 상속이라는 대가가 따른다.** 직접 받는 경로는 위장에 내성이 있고,
   ffmpeg 에 위임하는 경로는 ffmpeg 의 확장자 정책에 종속된다.
6. `200` + `text/html` 이 정상 세그먼트와 오류 페이지 **둘 다**를 뜻하므로, 선두
   바이트 판별 없이는 검증 도구가 정반대 결론을 낸다.
